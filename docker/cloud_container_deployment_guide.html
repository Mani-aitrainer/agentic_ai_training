1. Architectural Overview

Modern cloud engineering requires navigating both single-cloud and multi-cloud paradigms. Key primitives such as Resource Groups, Managed Application Hosting (App Service), and Container Registries (ACR/ECR) form the core building blocks for provisioning, isolating, and serving applications. When scaling containerized workloads to enterprise production, orchestrators like Amazon Elastic Kubernetes Service (AWS EKS) provide standard, highly available compute clusters.

2. Resource Groups (Azure vs AWS)

A Resource Group is a logical container that holds related resources for a cloud solution. Organizing cloud resources effectively ensures lifecycle management, governance, cost tracking, and access control.

Azure Resource Group (ARG)

In Microsoft Azure, every resource (Virtual Machine, App Service, ACR instance, SQL database) must belong to exactly one Azure Resource Group.

  • Lifecycle Boundary: Deleting a Resource Group automatically cascades deletion to all contained resources.
  • Access Control (RBAC): Role-Based Access Control permissions applied at the Resource Group level are inherited by all resources within it.
  • Deployment Scope: Azure Resource Manager (ARM) templates and Bicep files deploy directly target resource groups.

AWS Resource Groups & Tagging

AWS handles grouping differently. AWS resources exist independently inside a Virtual Private Cloud (VPC) or Region, but can be organized using AWS Resource Groups powered by resource tags.

  • Tag-Based Grouping: Resources sharing specific key-value tags (e.g., Environment=Production, Project=EKS-Microservices) are dynamically grouped.
  • AWS Systems Manager Integration: Enables bulk operations, patch management, and automated tasks across grouped resources.
  • Cost Allocation Tags: Used in AWS Cost Explorer to track spending per application lifecycle.

3. App Service & Managed Application Platforms

Azure App Service is an HTTP-based service for hosting web applications, REST APIs, and mobile backends. It provides automated scaling, SSL termination, continuous deployment, and built-in container execution.

Abstraction Level PaaS (High Abstraction) PaaS (High Abstraction) CaaS / Orchestration (Control & Flexibility)
Deployment Unit Code or Single Container Code or Single Container Multi-Container Pods & StatefulSets
Scaling Mechanism Auto-scale based on CPU/RAM rules Auto-scale concurrency rules Horizontal Pod Autoscaler (HPA) & Cluster Autoscaler / Karpenter
Networking & Mesh VNet Integration / Private Endpoints VPC Connector / Private Subnets Custom CNI (AWS VPC CNI), Istio / Linkerd Service Mesh

Architectural Guidance: App Service vs. EKS Use Azure App Service / AWS App Runner for standard web applications, monolithic APIs, or microservices with simple architectures. Transition to AWS EKS when you require fine-grained orchestration, multi-container pods, complex routing, service meshes, dynamic scheduling, or multi-cloud consistency.

4. Container Registries (ACR vs ECR)

Before deploying a container to an orchestrator like Kubernetes, the compiled Docker image must be stored in a secure, private container registry.

Azure Container Registry (ACR)

  • Managed private Docker Registry service based on the open-source Docker Registry 2.0.
  • Integrates directly with Microsoft Entra ID (Azure AD) for service principal authentication.
  • Supports OCI (Open Container Initiative) artifacts, Helm charts, and geo-replication across regions.

AWS Elastic Container Registry (ECR)

  • Fully managed container registry integrated with AWS IAM, offering encryption at rest via AWS KMS.
  • Supports repository policies, vulnerability scanning (via Amazon Inspector), and image tag immutability.
  • ECR Public & Private Repositories: Private registries isolate images inside your AWS account; ECR Public allows publishing public container images.

Authenticating and Pushing to AWS ECR

# 1. Authenticate Docker CLI to your AWS ECR registry
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com

# 2. Create ECR Repository (if not already existing)
aws ecr create-repository --repository-name my-app-repo --region us-east-1

# 3. Build and Tag your Docker image
docker build -t my-app:v1.0 .
docker tag my-app:v1.0 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app-repo:v1.0

# 4. Push image to ECR
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app-repo:v1.0

5. AWS EKS Kubernetes Architecture

Amazon EKS manages the availability and scalability of the Kubernetes control plane nodes (API server, etcd storage engine, scheduler). You provision worker nodes using AWS Managed Node Groups (EC2 instances) or serverless compute via AWS Fargate.

6. Step-by-Step EKS Deployment Guide

This section provides an end-to-end, production-ready operational guide for provisioning an AWS EKS cluster, building your application container, pushing it to ECR, and deploying it with Kubernetes manifests.

Step 1: Provision EKS Cluster via eksctl

Create a cluster configuration file named eks-cluster.yaml:

apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: prod-eks-cluster
  region: us-east-1
  version: "1.29"

managedNodeGroups:
  - name: general-nodes
    instanceType: t3.medium
    desiredCapacity: 3
    minSize: 2
    maxSize: 5
    privateNetworking: true
    iam:
      withAddonPolicies:
        albumController: true
        autoScaler: true
        ebs: true

Execute the cluster creation command:

# Provision the cluster (takes ~10-15 minutes)
eksctl create cluster -f eks-cluster.yaml

# Update local kubeconfig to point to new cluster
aws eks update-kubeconfig --region us-east-1 --name prod-eks-cluster

# Verify cluster nodes
kubectl get nodes

Step 2: Define Kubernetes Deployment & Service Manifests

Create a combined manifest file application.yaml containing the Deployment, ClusterIP Service, and HorizontalPodAutoscaler:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloud-app-deployment
  namespace: default
  labels:
    app: cloud-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cloud-app
  template:
    metadata:
      labels:
        app: cloud-app
    spec:
      containers:
      - name: cloud-app-container
        image: 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app-repo:v1.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        readinessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: cloud-app-service
  namespace: default
spec:
  type: ClusterIP
  selector:
    app: cloud-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cloud-app-hpa
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: cloud-app-deployment
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Step 3: Expose via AWS Application Load Balancer (Ingress)

Create ingress.yaml to trigger the AWS Load Balancer Controller to provision an internet-facing ALB:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cloud-app-ingress
  namespace: default
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: cloud-app-service
            port:
              number: 80

Step 4: Apply Manifests and Verify Deployment

# Apply all manifests to EKS cluster
kubectl apply -f application.yaml
kubectl apply -f ingress.yaml

# Verify Pod status
kubectl get pods -l app=cloud-app -o wide

# Check Service details
kubectl get svc cloud-app-service

# Retrieve ALB URL from Ingress
kubectl get ingress cloud-app-ingress

Production Readiness Checklist
  • IAM Roles for Service Accounts (IRSA): Avoid hardcoding AWS credentials inside container pods; bind Kubernetes service accounts to IAM roles.
  • Resource Quotas & Limits: Always set explicit CPU and Memory requests and limits to prevent noisy neighbor issues.
  • Node Group Autoscaling: Enable Karpenter or Cluster Autoscaler for dynamic node provisioning.
  • Container Security: Enable automated image scanning in ECR and use non-root base images.
