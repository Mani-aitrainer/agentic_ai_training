Section 19a · Azure Cloud Deployment

Resource Group, App Service, Container Registry

Three services you need before a single container runs on Azure.

Resource Group

The folder for everything

  • Every Azure resource belongs to exactly one resource group.
  • It is the unit for access control (RBAC), cost reporting and cleanup.
  • Deleting the group deletes everything inside it.

On AWS: no mandatory container. Teams use tags, Resource Groups (tag queries), CloudFormation stacks and separate accounts to get the same effect.

App Service

Managed hosting for web apps

  • App Service Plan = the compute: region, VM size, instance count, price tier.
  • Web App = your app running on that plan. Several apps can share one plan.
  • Built-in HTTPS, custom domains, deployment slots, autoscale.

On AWS: ECS Express Mode (Fargate + load balancer + autoscaling from one image) or Elastic Beanstalk. App Runner was the closest match but no longer accepts new customers.

Container Registry

Private home for your images

  • Stores Docker images with tags such as agent:1.4.0.
  • Tiers: Basic, Standard, Premium (Premium adds geo-replication and private endpoints).
  • Web Apps pull from it using a managed identity.

On AWS: Amazon ECR, with image scanning and lifecycle policies. ECS tasks pull using an IAM task execution role.

Same five moves on both clouds: build, push, point the compute at the image, configure, verify.

→
5 · VerifyHealth check, logs, browse

Azure Core commands

# 1-2 build and push
az acr login --name acragents
docker build -t acragents.azurecr.io/agent:1.0 .
docker push acragents.azurecr.io/agent:1.0

# 3 plan + web app (Linux)
az appservice plan create -g rg-agents-prod \
  -n plan-agents --is-linux --sku B1
az webapp create -g rg-agents-prod -p plan-agents \
  -n agent-api --container-image-name \
  acragents.azurecr.io/agent:1.0

# 4 tell Azure which port the app listens on
az webapp config appsettings set -g rg-agents-prod \
  -n agent-api --settings WEBSITES_PORT=8000

AWS Same flow

# 1-2 build and push
aws ecr get-login-password | docker login \
  --username AWS --password-stdin <acct>.dkr.ecr...
docker build -t <acct>.dkr.ecr.../agents:1.0 .
docker push <acct>.dkr.ecr.../agents:1.0

# 3-4 compute, two options
# a) ECS Express Mode: give it the image
#    + two IAM roles; it creates Fargate
#    service, load balancer and autoscaling
# b) Classic ECS: task definition (image,
#    port 8000, CPU/memory) + service
#    on Fargate behind an ALB
Port mismatchApp listens on 8000, platform probes 80. Set WEBSITES_PORT on Azure, containerPort on ECS.
Registry pull failsGrant AcrPull to the Web App's managed identity. On AWS, the task execution role needs ECR read.
Secrets in imagesNever bake API keys in. Use Key Vault references or Secrets Manager injected at runtime.
Cold startsEnable Always On (Azure) or keep a minimum task count (ECS) for latency-sensitive agents.
Trainer notes

Keep this at concept level: learners should be able to name each step and its AWS twin. The four gotchas cover most "it deployed but returns 503" questions in class.

Section 22a · Production-Ready Agentic Systems

Rate limiting & retries

A chatbot makes one LLM call per message. An agent can make ten. Limits that never bothered a chatbot will break an agent.

What is limitedTokens per minute (TPM) and requests per minute (RPM) per deploymentTokens and requests per minute per model, per Region (service quotas)

Retry

Exponential backoff + jitter

Wait 1s, 2s, 4s… plus a random offset so many agents don't retry at the same instant. Honour Retry-After when given. Cap the attempts.

Limit

Client-side token bucket

Throttle your own outbound calls to stay under the quota, rather than waiting for the provider to reject you.

Protect

Circuit breaker + idempotency

Stop calling a failing dependency for a short cool-off. Make tool calls safe to repeat, so a retry never books a payment twice.

Python Retry pattern (same on both clouds)

from tenacity import retry, stop_after_attempt, wait_random_exponential

@retry(wait=wait_random_exponential(min=1, max=30),
       stop=stop_after_attempt(5))
def call_llm(messages):
    return client.invoke(messages)  # raises on 429

Rule of thumb What to retry

  • Retry: 429, 500, 502, 503, 504, timeouts.
  • Do not retry: 400 (bad prompt), 401/403 (auth), content-filter blocks.
  • Put a limit on total agent steps as well, so a looping agent cannot burn the whole quota.
  • SDKs (boto3, openai) already retry a few times. Know their defaults so you don't stack retries on retries.
Trainer notes

Use the fan-out strip to make the point: a 10-call agent with 5 retries each can hit the provider 50 times for one user question. That is why limits belong in the design, not as an afterthought.

Section 22b · Production-Ready Agentic Systems

API Gateway / Reverse Proxy integration

Put one front door in front of your agent. It handles who can call, how often, and where the request goes, so the agent code doesn't have to.

Rate limits come in layers

GatewayPer client: "partner X gets 60 req/min"
Agent appPer user session: max steps, max tokens per task
ProviderHard ceiling: TPM / RPM quota on the model

Agent-specific watch-outs

  • Timeouts: agents can run long. API Gateway REST integrations default to a 29-second timeout; plan for streaming or async jobs.
  • Streaming: make sure the gateway/proxy passes server-sent events through without buffering.
  • Private backend: only the gateway should be able to reach the agent container.
Trainer notes

Link back to slide 4: the gateway protects you from your callers, retries protect you from your providers. Both are needed.

Production checklist

  • Image tagged by version, never only latest
  • Health-check endpoint the platform can probe
  • No secrets in the image or repo
  • Retries with backoff + jitter on LLM and tool calls
  • Max steps and max tokens per agent task
  • Gateway rate limits per client
  • Timeouts sized for long agent runs
  • Logs and traces for every step of the agent
  • Budget alerts on model and compute spend
