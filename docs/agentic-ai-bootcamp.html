01

What happened before LLM

Predictive models, deep learning, CNN, RNN, GAN, transformers, ChatGPT, agents, and the road to AGI

Six decades in one line

Every phase solved a limit of the one before it. LLMs are not a sudden jump; they sit on top of all of this.

Predictive AI, then deep learning

1990s – 2000s

Predictive AI models

Statistical and classical ML models (regression, decision trees, random forest, XGBoost) learn patterns from historical, structured data.

They predict one number or one class, and a human must hand-pick the features that matter.

Credit scoring and loan default prediction in banks
Sales and demand forecasting in retail
2006 – 2012

Deep learning models

Neural networks with many layers learn features automatically from raw data, so no manual feature engineering is needed.

They became practical once large datasets and GPUs arrived, and opened up images, audio, and text.

Voice assistants recognising speech (Siri, Google Assistant)
Auto-tagging faces and objects in Google Photos

CNN for images, RNN for sequences

2012 · AlexNet moment

CNN · Convolutional neural network

Slides small filters across an image to detect edges, then shapes, then whole objects, layer by layer.

It made computers genuinely good at seeing, and won ImageNet by a huge margin in 2012.

Face unlock on smartphones
Detecting pneumonia or fractures in X-ray scans
1997 LSTM · popular from 2014

RNN · Recurrent neural network

Reads data one step at a time and carries a memory forward, so word order and time order matter.

Its weakness: it forgets long context and cannot be parallelised, which transformers later fixed.

Next-word suggestion on mobile keyboards
Early Google Translate and speech-to-text

GANs create, transformers understand

2014 · Ian Goodfellow

GAN · Generative adversarial network

Two networks compete: a generator creates fake samples and a discriminator tries to catch them.

Both improve until the fakes look real. This was the first big wave of generative AI.

Realistic synthetic faces and deepfake videos
Synthetic training data and photo super-resolution
2017 · "Attention is all you need"

Transformer architecture

Self-attention lets every word look at every other word at once, so long context is understood in parallel.

Parallel training on GPUs made huge models possible. Every modern LLM is a transformer.

Google Translate's neural models
Google Search understanding queries with BERT (2019)

How each architecture "sees" data

ChatGPT evolution

Bigger

Parameters grew over 1,000x from GPT-1 to GPT-3, and so did the training data.

Aligned

RLHF turned a text predictor into an assistant that follows instructions. That is what made ChatGPT usable.

Agentic

Reasoning, tool use, and computer use moved models from answering questions to finishing tasks.

Agentic AI frameworks

An agent is an LLM in a loop: it plans, calls tools, looks at the result, and decides the next step until the goal is met.

Frameworks give you the loop, memory, tool calling, and multi-agent orchestration so you don't rebuild them each time.

Before GPT vs after GPT

Why AI moved from a few niches into every field, and why it happened now

Before GPT and after GPT

Before GPT (LLM)

AI was a specialist tool

  • Used only in certain fields: forecasting, stock price prediction, fraud, recommendations
  • One model per problem, trained on that problem's labelled data
  • Needed data scientists, feature engineering, and months of work
  • Worked mostly on structured tables of numbers
After GPT (LLM)

AI is a general-purpose layer

  • AI is creating a revolution in all fields: law, medicine, education, HR, software
  • One model handles thousands of tasks with just a prompt
  • Any developer can use it through an API in minutes
  • Works on documents, emails, code, images, and speech

The actual reason it impacts every field

Language is the interface

Every profession runs on language. When the input is plain English, anyone can use AI without writing code.

One model, many tasks

A single model summarises, translates, writes code, and reasons without retraining. You change the prompt, not the model.

Trained on the world's knowledge

Pre-training on huge text corpora gives broad knowledge of medicine, law, finance, and code in one place.

Unlocks unstructured data

Most enterprise data is unstructured: PDFs, emails, chats, claims. Old ML couldn't read it; LLMs can.

Delivered as an API

No ML team, no GPUs, no training. Pay per use and plug it into existing apps the same day.

It can act, not just answer

With tools and reasoning, LLMs complete multi-step work. That turns AI from insight into execution.

Why AI evolved now

Why GPUs changed the game

  • Big data existed by 2010, but CPUs could not process it fast enough to train deep networks
  • GPUs, built for gaming graphics, turned out to be ideal for neural network maths
  • NVIDIA's CUDA made GPUs programmable for AI, and the cloud made them rentable
  • Transformers were designed to run in parallel, so they scale with every GPU you add
Block 03

Why Agentic AI is more powerful

We already have the supporting blocks: APIs, CLI support, and tools. The agent only needs to use them.

  • Decades of software (REST APIs, CLIs, SDKs, databases, cloud consoles) are already machine-callable, so agents act on existing systems instead of needing new ones.
  • Standard protocols like MCP (Model Context Protocol) let one agent plug into GitHub, Jira, databases, and AWS in a consistent way.
  • LLMs can now reason, plan, and self-correct in a loop. Combined with tools, a model that answers becomes a model that gets work done.
04

Basic needs of calling LLMs

API key, model name, system and user prompts, temperature, top P, top K

Anatomy of an LLM call

Your first LLM call, in 15 lines

# pip install anthropic
import os
from anthropic import Anthropic

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

response = client.messages.create(
    model="claude-sonnet-5",          # which model
    max_tokens=500,                  # cap on output
    temperature=0.2,                 # low = focused
    system="You are an HR assistant. Reply in 3 bullets.",
    messages=[
        {"role": "user",
         "content": "Summarise a Java developer job role."}
    ],
)

print(response.content[0].text)
print(response.usage)   # input_tokens, output_tokens

Read it top to bottom

  • API key is read from an environment variable, never hard-coded
  • model picks capability and price
  • system sets the role and output rules
  • messages holds the user prompt and chat history
  • temperature and max_tokens shape the answer
  • usage tells you exactly what you'll be billed

The same shape works for OpenAI, Gemini, and Bedrock SDKs: only the client and model names change.

API key and model name

API key

A secret token that identifies your account and is used for billing and rate limits.

  • Store in .env or a secrets manager, never in Git
  • Use separate keys for dev, test, and prod
  • Rotate immediately if it leaks
  • On AWS, use IAM roles with Bedrock instead of keys
# .env  (add .env to .gitignore)
ANTHROPIC_API_KEY=sk-ant-xxxxxxxx

Model name

A string that selects the model family, tier, and version. It decides quality, speed, and cost.

ProviderExample model IDs
Anthropicclaude-opus-5 claude-sonnet-5
OpenAIgpt-6-astra
Googlegemini-3.1-pro
Open weightsdeepseek llama qwen

Pin a specific version in production so behaviour doesn't change under you.

System prompt vs user prompt

System prompt

Set once by the developer. Defines who the model is, the rules it must follow, and the output format. The end user usually never sees it.

User prompt

Changes on every request. It's the question, task, or data from the end user. Chat history is also sent as alternating user and assistant messages.

System
You are a recruitment assistant for Acme HR.
- Write job descriptions in a professional tone.
- Never mention salary unless provided.
- Output markdown with sections:
  Summary, Responsibilities, Requirements.
User
Create a job post for a Senior Java Developer,
Chennai, 6–9 years, Spring Boot and AWS.

Same user prompt + different system prompt = completely different output.

Temperature: how adventurous the model is

Temperature rescales the probabilities before the next token is picked. Range is usually 0 to 1 (some APIs allow up to 2).

ValueUse for
0 – 0.3Code, SQL, data extraction, facts
0.4 – 0.7Emails, summaries, chat
0.8 – 1.0Brainstorming, stories, taglines

Low temperature reduces randomness, not hallucination. Grounding and checks still matter.

Top P and top K: which words are allowed

  • Top K keeps only the K most likely next tokens, then samples from those.
  • Top P (nucleus sampling) keeps the smallest set whose probabilities add up to P.
  • Both remove the long tail of odd words. Temperature then decides how freely it picks within what's left.

Practical rule: tune temperature first and leave top P and top K at defaults. Many providers advise changing one, not both, and some newer models restrict combining them.

Anthropic exposes top_k; OpenAI exposes only top_p.

Parameter cheat sheet

ParameterWhat it doesTypical setting
api_keyAuthenticates and bills your accountFrom env var or secrets manager
modelChooses capability, speed, and priceSonnet for most work, Opus for hard, Haiku for fast

What's DeepSeek, and why is it so well known?

A Chinese AI lab (backed by the hedge fund High-Flyer) that released frontier-level models as open weights, at a fraction of the usual cost.

Dec 2024DeepSeek-V3: mixture-of-experts model, reported final training run ~US$5.6M
Jan 2025DeepSeek-R1: reasoning model matching OpenAI o1, MIT licence
2025–26Follow-up V3.x and newer releases keep pushing cost down

Why everyone talks about it

  • Open weights: anyone can download, run, and fine-tune it on their own servers
  • Low cost: showed top performance is possible without billion-dollar budgets
  • Visible reasoning: R1 shows its chain of thought
  • Market shock: topped app stores in Jan 2025; NVIDIA lost ~US$590B in value in a single day
  • Efficiency ideas: MoE and RL-first training were widely copied

Enterprise caution: data-residency questions for the hosted app; self-hosting the weights avoids that.

Running example: HR Recruitment module → job posting screen only.

Component 1 · Spec

The spec: a contract before code

A spec is a markdown file that describes the feature so precisely that an agent (or a new developer) can build it without guessing.

It should have

  • Goal and scope, plus an explicit out-of-scope list
  • User stories and roles
  • Screens, fields, and validation rules
  • API contract: endpoints, request, response, errors
  • Data model and statuses
  • Acceptance criteria that can be tested
  • Non-functional needs: performance, security, accessibility

Important points

  • Keep one spec per feature, stored in the repo (docs/specs/)
  • Write acceptance criteria as Given / When / Then so they become tests
  • Out-of-scope stops the agent from building extra features
  • Version it: update the spec first, then the code
  • Reference it from CLAUDE.md and skills with @docs/specs/…

Vague spec → the agent fills gaps with assumptions. Precise spec → predictable code.

Sample: job posting spec

Component 2 · Skills

Skills: reusable know-how, loaded on demand

A skill is a folder with a SKILL.md that teaches Claude how to do one kind of task your way. Only the name and description sit in context; the body loads when the task matches.

It should have

  • name and a description that says what it does and when to use it
  • Step-by-step instructions
  • Conventions, a checklist, and a definition of done
  • Optional scripts/, templates, and reference files

Important points

  • The description is the trigger: be specific
  • One skill, one job. Keep SKILL.md short; move detail to linked files
  • Lives in .claude/skills/ (project) or ~/.claude/skills/ (user)
.claude/skills/job-posting-ui/SKILL.md
---
name: job-posting-ui
description: Builds Angular screens for the HR
  job posting feature (list, form, detail). Use when
  creating or changing job posting UI components.
---
# Job posting UI
## Steps
1. Read @docs/specs/job-posting.spec.md
2. Generate standalone components in
   ui/src/app/features/job-posting/
3. Use a typed service for /api/v1/job-postings
4. Reactive forms with the spec's validation rules
5. Write component tests, run `npm test`

## Conventions
- Signals for state; new control flow (@if, @for)
- No business logic in templates
- All labels in the i18n file

## Done when
- Lint, tests, and build pass
- Every acceptance criterion is covered
Component 3 · Agent

Subagents: specialists with their own context

A subagent is a separate Claude instance with its own system prompt, tools, and model. The main agent delegates to it, and it returns only a summary, which keeps the main context clean.

It should have

  • A clear single role and a description of when to use it
  • A restricted tool list (least privilege)
  • A model choice suited to the job
  • A fixed output format

Important points

  • Reviewers should be read-only: no Edit or Write
  • Add "use proactively" to trigger it automatically
  • Lives in .claude/agents/; create one with /agents
.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews changed code for bugs,
  security issues, and spec compliance. Use
  proactively after any feature is implemented.
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior reviewer for the HR system.

Process
1. Run `git diff` to see what changed
2. Compare against docs/specs/*.spec.md
3. Check: validation, error handling, SQL
   injection, secrets, tests, naming

Output
| Severity | File:line | Issue | Fix |
Severity = Critical, High, Medium, Low.
Never edit files. Report only.
Component 4 · Example skill

Create a log analyzer skill

It should have

  • The log sources and formats it understands (CloudWatch, Spring Boot, Angular console)
  • How to narrow the time window and group errors by signature
  • How to trace a request ID across UI → Lambda → DB
  • How to map a stack trace to the source file and line
  • A fixed report format with the likely root cause

Important points

  • Mask secrets and personal data in the output
  • Put heavy parsing in a script so it's fast and repeatable
  • Suggest a fix, but don't apply it without approval
.claude/skills/log-analyzer/SKILL.md
---
name: log-analyzer
description: Analyses application and Lambda
  logs to find errors and root causes. Use when
  the user shares logs, a stack trace, or says
  something failed in dev, test, or prod.
---
## Steps
1. Run scripts/parse_logs.py on the log file
   (groups ERROR/WARN by exception + message)
2. Find the first occurrence and frequency
3. Follow requestId across services
4. Open the source file from the stack trace
5. Check recent commits touching that file

## Report
- Summary (1 line)
- Top errors: count, first seen, signature
- Root cause hypothesis + evidence
- Suggested fix and a test to prove it

## Never print tokens, passwords, emails, IDs

Component 6 · Rules

Rules: standards that must always hold

Rules are short, always-on instructions. They live in CLAUDE.md or as separate files in .claude/rules/, optionally scoped to file paths so they load only where relevant.

It should have

  • Coding standards and naming conventions
  • Security rules: secrets, input validation, SQL
  • Testing requirements and coverage expectations
  • Architecture boundaries: what may call what
  • Things the agent must never do

Important points

  • Short, testable statements, not essays
  • Rules guide; hooks and CI enforce. Use both for critical rules
  • Add a rule whenever you correct the agent twice
.claude/rules/java-api.md
---
paths:
  - "api/**/*.java"
---
# Java API rules
- Java 21, constructor injection only
- Controller → Service → Repository;
  controllers hold no business logic
- Validate every request DTO with
  jakarta.validation annotations
- Use prepared statements; never
  concatenate SQL
- Return RFC 7807 problem+json errors
- Every public service method has a
  unit test (JUnit 5 + Mockito)

  Manager, never from code

From proposal to implementation, and how to structure the repo so the agent sees the whole system

The process: think first, then build

Documents are the memory

Proposal, plan, and spec live in docs/. Every new session reads them instead of relying on chat history.

Opus plans, Sonnet builds

Use the strongest model for steps 1–3, a different vendor's model for step 4, and a fast model for routine coding in step 5.

Cheap to fix on paper

A wrong assumption caught in the spec costs one edit. Caught after implementation, it costs a rewrite.

Why a monorepo works so well with coding agents

  • The agent captures end-to-end system knowledge: UI, API, DB, and infra in one place
  • One change can span layers: add a field to the spec, the DB migration, the Java DTO, and the Angular form in a single task
  • Contracts stay in sync because the agent can read both sides of every API call
  • One set of rules, skills, and agents serves the whole team
  • One PR shows the complete impact for review

Folder-level CLAUDE.md

Claude reads the root CLAUDE.md at start-up, and folder-level files when it works inside that folder. Each one is a briefing for that part of the system.

What it should have

  • Purpose of the folder in one or two lines
  • Tech stack and versions
  • Exact commands: install, run, test, build, lint
  • Folder structure and where new code goes
  • Conventions and patterns to copy
  • Gotchas and things to never do
  • Links to specs with @path imports

Keep it under ~200 lines. Use /init to generate a first draft.

signals, SCSS. Hosted on S3.

## Structure

src/app/features/    one folder per feature
src/app/shared/      reusable UI

User-level vs project-level folders

~/.claude/ (your machine, all projects)

User level

  • ~/.claude/CLAUDE.md: personal preferences ("explain before large edits", "use British English")
  • ~/.claude/skills/: personal skills you use everywhere, like log-analyzer
  • ~/.claude/agents/: personal subagents
  • ~/.claude/settings.json: default model, global permissions

Not shared with the team. Never put project facts here.

<repo>/.claude/ (committed to Git)

Project level

  • CLAUDE.md at root and per folder: architecture, commands, conventions
  • .claude/rules/: team coding standards
  • .claude/skills/, .claude/agents/: shared workflows and reviewers
  • .claude/settings.json: team permissions and hooks
  • .mcp.json: shared MCP servers
  • settings.local.json, CLAUDE.local.md: your overrides, git-ignored

Precedence: project settings override user settings, and local overrides beat both. Enterprise-managed policy sits above all.

Models, tokens, and billing

Which model for which job, what a token is, and how the bill is calculated

What model for what purpose

Opus 5

deepest reasoning
  • Complex reasoning and architecture
  • Proposal and plan creation
  • Complex feature implementation
  • Hard debugging and code review

Sonnet 5

everyday workhorse
  • Day-to-day coding tasks
  • Normal feature implementation
  • Tests, refactors, bug fixes
  • Best balance of cost and quality

Haiku 4.5

fastest, cheapest
  • Email drafts
  • Data summarisation
  • Classification and extraction
  • High-volume, low-latency calls

Above Opus sits the Mythos tier (Claude Fable 5.1) for the hardest problems. In Claude Code, switch any time with /model.

What does "token" mean?

A token is a chunk of text the model reads and writes: a word, part of a word, or punctuation. Models never see characters, only token IDs.

Create a job posting for SpringBoot developers.

Illustrative split: 10 tokens. Exact splits differ by model tokenizer.

Rule of thumb

1 token ≈ 4 English characters ≈ ¾ of a word. 1,000 words ≈ 1,300–1,500 tokens.

Code and other languages

Code, JSON, and Tamil or Hindi text usually use more tokens per word than plain English.

Tokenizers differ

The same text can cost a different number of tokens on different models. Claude 4.7+ produces roughly 30% more tokens for the same text.

Ways to pay less

  • Prompt caching: repeated input read from cache at ~10% of the input price
  • Batch API: 50% off for jobs that can wait hours
  • Right-size the model: don't send Haiku work to Opus

Input token vs output token

Input tokens are everything you send: system prompt, user prompt, chat history, files, and tool results.

Output tokens are everything the model writes, including thinking and tool calls.

Output costs 5x more because input is processed in one parallel pass, while output is generated one token at a time, each needing a full pass through the model.

Why agents get expensive

The model has no memory. Every turn resends the whole conversation, so input grows with each step of an agent loop.

  • Use /clear between unrelated tasks and /compact for long ones
  • Subagents keep big searches out of the main context
  • Prompt caching makes the repeated prefix cheap
  • Check spend with /cost or the Console usage page

Block 09

Code review: write in one model, review in another

Why it works

  • Models from the same vendor share blind spots; a different vendor catches different bugs
  • The author model tends to approve its own reasoning
  • Disagreements between models point to real ambiguity

How to run it

  • Give the reviewer the spec and the diff, not the whole repo
  • Ask for Critical / High / Medium / Low with file and line
  • Use Codex CLI, Gemini CLI, or an API call from a script or CI
  • The human always makes the final call

Loop engineering and harness engineering

Loop engineering

Designing the cycle the agent repeats until the work is done: plan → act → verify → repeat.

  • Define "done" up front: tests pass, build green, criteria met
  • Give fast, objective feedback: tests, linters, type checks, screenshots
  • Work in small increments so each loop is easy to verify
  • Set stop conditions: max iterations, budget, ask a human when stuck
  • Feed repeated mistakes back into rules and CLAUDE.md

Harness engineering

Designing everything around the model: the environment that makes an average run a good run.

  • Context: CLAUDE.md, specs, and skills give the right information at the right time
  • Tools: only what's needed, with clear descriptions
  • Guardrails: permissions, sandbox, deny lists
  • Hooks: auto-run format, lint, and tests after every edit
  • Context hygiene: subagents and compaction keep it focused

Same model, better harness, better results. Claude Code itself is a harness around Claude.
